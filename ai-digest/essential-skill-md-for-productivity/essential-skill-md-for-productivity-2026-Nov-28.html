1. Copilot CLI 1.0.117 reaches stable with tighter MCP and extension approvals, and 1.0.118 pre-releases keep Git hooks read-only in sandboxes

GitHub promoted Copilot CLI 1.0.117 to stable on 27 Nov at about 13:04 UTC. That brings the safety fixes from the pre-releases we covered yesterday to every user. Approving an MCP server's tools no longer also approves built-in actions such as shell commands. Autopilot now asks before starting each extension. Rejecting a Forge draft puts back a skill's original files. The stable notes add more for teams that use custom agents. A custom agent can now list exactly which tools it gets. Subagents follow the tool list in their agent file even when the file has no prompt. Background agents can carry on after a restart. In plan mode, Assisted Permissions now asks before it creates a branch or installs a package. The first 1.0.118 pre-releases followed the same day. In 1.0.118-0, organization custom agents use the model they were configured with when --model isn't set. In sandboxed repos that have write access through readwritePaths, Git config and hooks stay read-only. A null anyOf in an MCP tool's output schema no longer breaks turns. In 1.0.118-1, running copilot mcp enable and disable at the same time no longer loses changes.

Sources: Copilot CLI 1.0.117 release notes, Copilot CLI 1.0.118-0 release notes, Copilot CLI 1.0.118-1 release notes, @github/copilot on npm

2. The skills CLI 1.9.1 stops removals from deleting the wrong copy of a skill and makes frozen-lockfile installs truly reproducible

Vercel Labs released version 1.9.1 of the open skills CLI (npx skills) on 27 Nov at about 05:08 UTC. It contains 13 fixes from eight contributors, and most of them make installed skills safer to remove and update. Removing a skill through a symlinked agent folder no longer deletes the shared original (#2804). A global removal no longer deletes a project's own skills (#2801). Symlinked paths to the same skill are now shown as one entry (#2671). With --frozen-lockfile, sync now fetches remote skills at the exact commit recorded in the lockfile (#2776). Together with the commit pinning added in 1.9.0, this makes an install from the lockfile reproducible. The CLI also won't overwrite a global lock file it can't read (#2779). Update now lists skipped global skills instead of saying everything is up to date (#2792), and check shows GitHub compare links for project skill updates (#2787). Skill downloads that never get a response now time out (#2822). For anyone who keeps one set of skills linked into several agents, this is a worthwhile update.

Sources: vercel-labs/skills v1.9.1 release, skills on npm

3. OpenClaw 2026.12.1-beta.1 lets you browse ClawHub skills by category and turn individual plugin tools on or off, a day before old config stops working

OpenClaw published 2026.12.1-beta.1 as a pre-release on 28 Nov at about 00:21 UTC (npm shows 27 Nov, 22:56 UTC). The skills changes are small but practical. You can browse and search the ClawHub catalog by category, and installed skills open as full pages instead of dialogs (#202756, #202581). In Settings, you can now turn individual tools from a plugin on or off instead of the whole plugin (#201453). Agent Templates can be shared from an agent's menu and previewed without expanding their files into the chat (#201644, #202060). Subagents no longer drop completions or send duplicate final replies to the parent (#204260, #204178). The release also lists dozens of Doctor deprecations with a 29 Nov 2026 deadline. They include bundled plugin load paths, CLI backend plugin registration, the web-fetch and web-search plugin config, and the MCP transport and timeout aliases. Anyone running OpenClaw with older plugin or MCP config should run Doctor now, before those aliases stop being migrated.

Sources: OpenClaw v2026.12.1-beta.1 release, openclaw on npm

4. Google fixes its Cloud Operator skills to always call at organization level, wait out access delays, and not claim work has started too early

A day after adding an admin setup skill for Cloud Operator, Google pushed three follow-up commits to its public skills repo on 27 Nov. Each one fixes a way the skills misled users. Commit 4d3b452 makes the cloud-operator and cloud-operator-setup skills always call the operator with an organization, never a project, because Cloud Operator only accepts organization-level calls. A 'not available in this project' error is no longer taken to mean the service is off, and notes saved after such a failed call are retried. Commit 10c799e (cloud-operator-setup 1.5.0, cloud-operator 1.6.0) covers a delay in access. Access in a user's home organization is granted automatically, but only a few minutes after someone there first uses an agent. So instead of sending the user to an admin, the skills now wait and retry about every two minutes for up to about ten minutes. Commit 27c1bea (cloud-operator 1.4.1) stops the agent from saying the operator is 'working on it' before the call has been sent or approved. All three are good examples of checking a skill's status messages, not just its commands, against how the product really behaves.

Sources: google/skills commit 4d3b452 (organization-only calls), google/skills commit 10c799e (wait for home-org access), google/skills commit 27c1bea (status wording)
