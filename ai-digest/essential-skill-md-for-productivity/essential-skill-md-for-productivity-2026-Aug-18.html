1. Claude Cowork reaches the Chrome side panel — Skills and Connectors now run in the browser

On August 12, Anthropic turned the Claude in Chrome side panel into a full Claude Cowork client: conversations now save to history, a task started in a browser tab can be picked up and finished on desktop, web, or mobile, and — most relevant to a skill library — Skills and Connectors already configured on an account work directly from the browser with no extra setup. Connectors bridge Claude to external tools like Gmail, Google Drive, and Slack over MCP, and Claude in Chrome can already see the current page and act on it using a person's existing logins (clicking, navigating, filling forms), so a skill can now drive an in-browser workflow the same way it drives a desktop one. The rollout follows July 21's "Record a Skill" feature, which let Pro/Max/Team users screen-record a task and get back a reusable skill; together the two updates push Cowork toward being the single surface where a skill is captured once and runs everywhere. It's live today on Max and Team plans, with Pro access rolling out in the coming weeks.

Sources: Claude (official), 9to5Mac, The New Stack

2. New study: loading a skill can make an agent measurably worse, not just better

A paper posted August 12 by researchers at Huazhong University of Science and Technology, Microsoft Research, Microsoft, and UIUC (arXiv 2608.11888) pushes back on the assumption that a loaded skill can only help. The authors built a differential-analysis framework that attributes a specific task failure or cost regression to the skill that caused it, by comparing a skill-guided run against a no-skill or semantically matched reference run — isolating skill quality from ordinary model variance at scale for the first time. The headline finding confirms what earlier reports had only hinted at: some skills measurably increase token use and execution time, and a subset actively lower task success rather than leaving it unchanged, meaning a skill library can silently make an agent worse if nobody is auditing outcomes rather than just intentions. For anyone assembling a productivity skill set, it's a concrete argument for benchmarking every installed skill before and after adoption, not just reviewing it for security.

Sources: arXiv abstract, arXiv full text

3. Largest audit yet of public SKILL.md files: 91.8% of 138,000 carry a real defect

A separate paper posted August 10 (arXiv 2608.08453) is the largest audit yet of what's actually inside public SKILL.md files: 138,133 files pulled from 20,556 GitHub repositories, scored against a two-tier defect taxonomy grounded in the official Agent Skills spec and best-practice guidance. The headline number — 91.8% of skills contain at least one detected defect — holds steady (88.8-94.6%) whether the researchers apply a lenient or strict threshold. Crucially, the dominant problems aren't exotic prompt-injection or supply-chain attacks; they're mundane packaging failures: weak routing metadata that stops an agent from selecting the right skill in the first place, bloated or non-actionable instruction bodies, and poorly organized supporting resources. It's a sobering complement to the GitSkills sprawl numbers reported in this digest on August 13 (3.8M files, 1.9M distinct): scale without curation is producing an ecosystem where the typical public skill isn't dangerous, just badly built and unlikely to actually help the agent that loads it.

Sources: arXiv abstract, arXiv full text

4. Claude Code v2.1.233 adds per-user spend attribution and memory limits for Bash — the guardrails a shared skill deployment needs

Claude Code's August 14 release, v2.1.233, is a smaller engineering update but a meaningful one for teams running skills in shared or metered environments. It adds GitLab merge request URL support to the --worktree flag and the claude agents view (MRs now display as !N, matching how GitHub PRs already show), an opt-in forward_user_identity apps-gateway setting that sends a signed-in user's identity as headers so a proxy behind the gateway can attribute spend per user, opt-in memory-cgroup limits for Bash tool commands on Linux so a runaway build can't stall a whole session, and a configurable CLAUDE_CODE_WEBFETCH_CACHE_TTL_MS environment variable for the WebFetch session cache. None of it is skill-specific, but per-user spend attribution and memory isolation are exactly the primitives an organization needs before it can safely let many people run many third-party skills against a shared Claude Code deployment without one bad actor, or one memory leak, taking the session down for everyone else.

Sources: GitHub Releases, Claude Code changelog
