# Daily Research Digest → bennyfoo / ai-digest

A topic-agnostic skill for recurring research that ends in a **published HTML page** and a **repo-stored knowledge base**. The **topic is supplied by the invocation**, never hardcoded here, so one skill can power many scheduled digests, each with its own folder and KB file.

This skill is designed to run **unattended in a cloud scheduled task (remote routine)**. Do not pause to ask the user questions mid-run — make reasonable defaults and note any assumptions in the digest itself.

This copy of the skill publishes into **bennyfoo** (github.com/bennyfoosandbox-lang/bennyfoo), Benny Foo's profile site (live at `https://bennyfoo.vercel.app/`), under an **`ai-digest/`** subfolder — **not** the repo root. The repo root is the profile homepage; never write to it from this skill except to add a one-time nav link (see Step 7). See `references/publishing.md` for the full layout and design-system rationale.

## Inputs (read from the invocation prompt)

- **TOPIC** (required): the subject, e.g. `Using AI for Business Productivity`. If missing entirely, ask once — it's the one thing with no safe default.
- **CADENCE** (default = daily): sets the freshness window. Daily → 24h, weekly → 7d, custom → one interval.
- **REPO_DIR** (default = `ai-digest/` inside the current git repo root): the working copy this session is running in. Always confirm the repo is `bennyfoosandbox-lang/bennyfoo` and that you're writing under `ai-digest/`, never the repo root.
- **PUBLISH_BRANCH** (default = the repo's default branch, usually `main`): the branch Vercel deploys from. Digests are committed here.
- **SOURCE_SPLIT** (default = 75 web search + 25 Firecrawl): how many candidate items to gather from each engine. Firecrawl is a metered/free-tier connector — treat 25 as a ceiling, not a target, and degrade gracefully to web-search-only if Firecrawl is unavailable or out of credits.

## Derived paths (compute once at the start)

Let `slug` = TOPIC lowercased, non-alphanumerics → single hyphens, trimmed (e.g. `using-ai-for-business-productivity`).

- Digest folder: `REPO_DIR/{slug}/` → i.e. `ai-digest/{slug}/`
- Digest file for this run: `ai-digest/{slug}/{slug}-{YYYY}-{MMM}-{DD}.html` where MMM is the 3-letter month (e.g. `2026-Jul-20`). This is the requested `topic-yyyy-MMM-dd` convention.
- Per-topic index: `ai-digest/{slug}/index.html` (a landing page listing every digest, newest first)
- AI Digest hub: `ai-digest/index.html` (lists every topic and links into each topic's index — this is **not** the site root; the site root `bennyfoo/index.html` is the profile homepage and is never regenerated by this skill)
- Knowledge base (separate folder, as requested): `ai-digest/knowledge-base/{slug}.md` — Markdown with a YAML frontmatter block. See **Knowledge base format** below.
- Template assets: `assets/digest-template.html`, `assets/index-template.html`, `assets/root-index-template.html` inside this skill — HTML shells already wired to bennyfoo's real stylesheet/fonts and carrying the runtime citation-liveness checker. Read them and fill their placeholders; never hand-write the shell/JS, and don't add inline `<style>` blocks — the design lives in `bennyfoo/assets/css/main.css`.

## The run, end to end

### Step 1 — Load the knowledge base (dedup memory)

Read `ai-digest/knowledge-base/{slug}.md`.
- If it does not exist, this is the **first run** for TOPIC. Everything found is new; create the file in Step 5.
- If it exists, parse the YAML frontmatter's `entries` list. Each entry has a `fingerprint` (a short stable slug for the development, e.g. `openai-enterprise-agent-builder`), a `title`, `first_seen`, the `digest` it appeared in, and one or more `urls`. Together the fingerprints + urls are this run's **dedup set**.

### Step 2 — Gather fresh, time-sensitive sources

Compute the freshness cutoff from CADENCE (daily → last 24h). Gather **on the order of 100 candidate items** so the ranking in Step 4 is meaningful — do not stop as soon as you have five.

- **Web search (~75 candidates):** issue several time-scoped queries that surface *news* (announcements, launches, studies, funding, incidents, regulation) rather than evergreen "best tools" listicles. Add recency qualifiers and prefer the last 24h. Vary the angle (product, enterprise adoption, research, policy) so coverage is broad.
- **Firecrawl (~25 candidates, hard ceiling):** use `firecrawl_search` with `tbs` set to the last day for freshness, and `firecrawl_scrape` only when a promising result needs its full text. Firecrawl returns richer full-page content and is best spent on the few most promising leads, not routine queries. If Firecrawl errors or is out of credits, log that in the digest footer and continue on web search alone — never fail the whole run over Firecrawl.

For every candidate, record **all** sources that mention it (not just the first). This mention count feeds ranking. Apply the freshness window at gather time (sort by "new", scope queries to the last day), not only when filtering later.

If the primary 24h window yields fewer than 5 dedup-passing items, widen in steps (24h → 48h → 72h → 7d, ceiling ~30d) until 5 are found or the ceiling is hit. Fallback relaxes *recency*, never *novelty* — items still must pass dedup. A thin digest (fewer than 5) is a valid, honest outcome; padding with filler is worse. Note the real age of any fallback item (e.g. "from earlier this week").

### Step 3 — Filter against the dedup set

For each candidate, derive its `fingerprint` and compare against the KB:
- Same fingerprint already logged, or a citation URL already in the KB → **discard as already-covered**, unless there's a *materially new development* (a number changed, a launch shipped that was only rumored before) — then keep it as an update and say so.
- Otherwise it's new and eligible.

Only new, in-window items proceed.

### Step 4 — Synthesize the top 5

Rank survivors by (a) relevance and impact to TOPIC and (b) how many independent sources corroborate them — neither factor alone dominates. Consolidate near-duplicate coverage into one item but keep every contributing source in that item's citations.

For each of the top ~5, write a **fuller paragraph (3–5 sentences)** in your own words: what happened, why it matters to TOPIC, key numbers/context. Never quote source text at length. Give each item a short punchy headline.

**Citations are mandatory and go at the end of each item** as real links to the actual article URLs (a bare publication name is not a citation). Every item needs at least one working link; an item with none is dropped. List all corroborating sources, each as its own link — this is also what the runtime liveness checker will probe.

### Step 5 — Update the knowledge base

Write `ai-digest/knowledge-base/{slug}.md`:
- Update frontmatter scalars (`last_run`, increment `run_count` and `digest_count`).
- Append one `entries` item per newly-published topic, with `fingerprint`, `title`, `first_seen` (today), `digest` (this run's filename), and `urls` (all citations).
- Append a dated section to the human-readable body with one bullet per new item linking to this digest.
- On first run, create the file with the full frontmatter + body header first.

Be thorough here even if the digest was trimmed for readability — this file is next run's dedup memory. See **Knowledge base format** for the exact shape.

### Step 6 — Render the HTML digest

Read `assets/digest-template.html`. Fill its placeholders (see the comment block at the top of that file for the full list): title, topic, human date, generated-at timestamp, the run tally, the source/Firecrawl notes, and the `{{ITEMS}}` block. Render each item as **static HTML** (headline + paragraph + a citations line) so the content is fully readable even where JavaScript doesn't run (e.g. GitHub's in-repo file viewer). The template's built-in JS only *enhances* citations with a best-effort liveness dot — it is never required to see the content. Each citation must follow the exact anchor + status-dot markup the template documents (`<a class="cite">` immediately followed by `<span class="link-status" data-url="...">`), or the checker won't find it. Item wrappers use `class="digest-item"` and the citations line uses `class="digest-sources"` — match the template's existing markup exactly, don't rename classes.

Write the filled HTML to `ai-digest/{slug}/{slug}-{YYYY}-{MMM}-{DD}.html`. Then regenerate `ai-digest/{slug}/index.html` from the list of digest files in that folder (newest first) using `assets/index-template.html`.

Finally regenerate the **AI Digest hub** `ai-digest/index.html` from `assets/root-index-template.html` so this (and any other) topic shows up there. Discover topics by scanning directories directly under `ai-digest/`, skipping `knowledge-base`: a directory is a topic if it contains an `index.html`. For each, read its title from `knowledge-base/{slug}.md` frontmatter (`topic:`), count its `{slug}-*.html` digest files, and find the latest by the date in the filename. Emit one card per topic, most-recently-updated first. See `references/publishing.md` for the exact card markup and how to write/carry forward each topic's short tag + description.

### Step 7 — Wire up site navigation (first topic only)

If `ai-digest/` doesn't exist yet in the repo when this run starts, this is the very first digest topic being added to the site — after writing everything above, also add an "AI Digest" link to the nav and footer of `bennyfoo/index.html` and every `bennyfoo/utilities/*.html` page (see `references/publishing.md` for the exact pattern). Skip this step on every subsequent run; the link only needs adding once.

### Step 8 — Publish to GitHub

Commit and push to PUBLISH_BRANCH so Vercel serves it. Include the new digest, the updated topic index, the updated AI Digest hub, and the updated `knowledge-base/{slug}.md` in one commit:

```
git add "ai-digest/{slug}/" "ai-digest/knowledge-base/{slug}.md" "ai-digest/index.html"
git commit -m "digest({slug}): {YYYY-MMM-DD} — N new items"
git push origin {PUBLISH_BRANCH}
```

Retry a failed push up to 4 times with exponential backoff (2s, 4s, 8s, 16s) — only for network errors. If the working copy isn't the publish branch or a push is rejected for non-network reasons, stop and report rather than force-pushing.

### Step 9 — Report

End with a one-line tally: `N new items published · M already-known items skipped · digest: <bennyfoo.vercel.app URL to this file>`. If nothing was new, still publish a short "nothing new since last run" digest and say so — silence is indistinguishable from a broken task. If Firecrawl was skipped, note it here.

## Knowledge base format

`ai-digest/knowledge-base/{slug}.md` is Markdown with a YAML frontmatter block. Frontmatter is the machine-readable dedup set; the body is a human-readable log.

```markdown
---
topic: "Using AI for Business Productivity"
topic_slug: using-ai-for-business-productivity
created: 2026-07-20
last_run: 2026-07-20
run_count: 1
digest_count: 1
entries:
  - fingerprint: openai-enterprise-agent-builder
    title: "OpenAI ships an enterprise agent builder"
    first_seen: 2026-07-20
    digest: using-ai-for-business-productivity-2026-Jul-20.html
    urls:
      - https://example.com/openai-agents
      - https://example.com/coverage
---

# Knowledge Base — Using AI for Business Productivity

Running log of everything already covered, newest first. Each bullet links the digest it appeared in.

## 2026-Jul-20 (baseline run)
- **OpenAI ships an enterprise agent builder** — no-code workflow agents for back-office tasks. [digest](../using-ai-for-business-productivity/using-ai-for-business-productivity-2026-Jul-20.html)
```

Keep fingerprints lowercase, hyphenated, and stable; reuse an existing one rather than minting a near-duplicate. This is what makes dedup reliable across months of runs.

## Publishing & hosting

See `references/publishing.md` for the full `ai-digest/` layout inside bennyfoo, why the templates link the site's real CSS/fonts instead of being self-contained, and the exact hub/index card markup. The site is already live on Vercel — there is no hosting setup left to do.

## What this skill does not do

- Does not scrape X/Twitter, TikTok, or Instagram — they block most crawlers including Firecrawl. If that coverage matters it needs a laptop-on tool.
- Does not claim a citation is verified dead/alive with certainty — the runtime check is **best-effort** (browsers can't read cross-origin HTTP status; see the template). It flags gross failures and offers a manual re-check; it is an aid, not a guarantee.
- Does not force 5 items — a short, honest digest beats padding.
- Does not force-push or rewrite history; it only appends commits to the publish branch.
- Does not touch `bennyfoo/index.html`, `bennyfoo/utilities/`, or anything outside `ai-digest/` except the one-time nav-link addition in Step 7.
